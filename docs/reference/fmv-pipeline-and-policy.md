# FMV pipeline and pre-trade policy detail

Moved verbatim from CLAUDE.md (BUI-1301).

### The FMV pipeline shells out across package boundaries
`comic-fmv` (apps/fmv) does **not** import eBay code — at runtime it shells out to the `ebay-sold-comps` **console script** installed on PATH. So both `apps/ebay` and `apps/fmv` must be `uv tool install`ed for FMV to work end to end (that's what `scripts/install.sh` guarantees). A `ModuleNotFoundError` or "command not found" from `comic-fmv` usually means the install step was skipped or a stale wrapper is shadowing the uv-installed binary (see BUI-27, documented in install.sh). **Sold comps come from one provider, sold-comps.com** (BUI-545 made it primary after eBay login-walled logged-out sold search ~2026-07-23; BUI-1239 removed the dead SerpApi fallback). Key `SOLD_COMPS_KEY` in `apps/ebay/.env` is **required**: `ebay-sold-comps` exits 2 without it. Every `queries_used` entry stays provider-tagged, and a failed fetch still classifies fetch-err (BUI-536). Historic `serpapi`-tagged ledger rows, cache entries, and captures stay readable (`parse_comp`, `backfill_comps_ledger.py`).

**Deploy the comics server before a client that speaks certifier (BUI-930).** The graded (slab) FMV mode added a `certifier`/`label` price identity (BUI-924/925) that an old comics server's `GET /api/comics` won't echo. `comic-fmv` probes for that before pricing any certified row and refuses every certified target (`skipped_schema_mismatch`) rather than risk a slab price landing on a raw row at the same grade — so deploy the server first; a client that runs ahead of it degrades safely (raw rows price normally, certified rows wait) rather than corrupting a price.

### gixen-overlay's FMV-aware pre-trade policy checks (BUI-617/619/620)
`plugins/gixen-overlay/src/gixen_overlay/policy.py` contributes five of the **six** pre-trade check codes (`unpriced_entry`, `over_fmv`, `recomputed_cap`, `fmv_staleness`, `duplicate_comic` — its `_CHECKS` tuple at `policy.py:666-672`) into gixen-cli's single check point via the `check_bid_write` hookspec; the sixth code, `exposure_ceiling`, plus the shared `POLICY_BLOCK_<CODE>` blocking mechanism, are host-owned and documented in `packages/gixen-cli/CLAUDE.md`'s "Policy checks" section. The overlay has no CLAUDE.md of its own, so its two operator-facing threshold env vars are documented **here** rather than there:

- **`POLICY_FMV_MULTIPLE`** (`policy.py:399`) — default **1.0**; `over_fmv` advises when `max_bid` exceeds this multiple of summed linked FMV highs (a slab's bid basis `bid_high`, not its widened published high, BUI-1262).
- **`POLICY_FMV_STALE_DAYS`** (`policy.py:519`) — default **30.0**; `fmv_staleness` advises when a linked FMV row is older than this many days.

Unlike the host's `POLICY_EXPOSURE_CEILING` (no default — unset disables that check entirely), both overlay defaults are **non-disabling**: leaving them unset does not turn the check off, it falls back to the default (contrast comment at `policy.py:176-177`). Read per request, never cached (KTD2) — edit `~/.comics-server/.env` and `launchctl kickstart`, no deploy.

**`FMV_CEILING_CAP`** (`apps/fmv`, BUI-1028) — unset/off by default; `1` makes `comic-fmv` give a raw `one_sided`/`too_wide` refusal with at least two comps at or above the target grade a bid cap (`fmv_math.ceiling_cap`: 0.60 x the lowest at-or-above rung's median, rounded down) stored in `fmv.ceiling_cap` with `pricing_basis='ceiling'`, `flag_reason` kept and `fmv_low`/`fmv_high` null. Read per call in the client, never cached. Deploy the comics server first (it adds the column and widens the `pricing_basis` CHECK on start); an older server rejects the write and the row stays refused. `over_fmv`/`recomputed_cap`/`unpriced_entry` measure a bid against the cap (factor 1.0) when `high` is null and `ceiling_cap` is set.

**Median bid cap (BUI-1219)** — a raw direct row in the VERY HIGH, HIGH, or MEDIUM bid tier with no photo haircut bids `clean_round(1.00 x median)`, at most `fmv_high`; every other row keeps `bid_factor x fmv_high` (spec §6). The median and tier persist in `fmv.median`/`fmv.bid_tier`, which `comic-fmv`'s cache hit and `recomputed_cap` (`max(rung x high, min(median, high))`) read; `plugins/gixen-overlay/tests/test_fmv_rung_parity.py` pins the two against `fmv_math`. Deploy the comics server first: an older server drops both fields, so its rows stay on `0.80 x fmv_high` and `recomputed_cap` advises on median bids.

**Best-offer comps (BUI-1234)** — sold-comps.com `soldPrice` on a best-offer sale is the LIST price (BUI-1222). The parser carries `bestOfferAccepted` as `best_offer`, the ledger stores it in `comps.best_offer` (filled on a later sighting, never overwritten), and `fmv_math.graded_pool` scales flagged slab comps by `BEST_OFFER_ACCEPTED_RATIO` (0.89) at pricing time. Stored prices stay the provider's number. The raw pool is not scaled (no accepted-price backtest yet). Deploy order is free; until the server is deployed, ledger re-reads stay at list.

**Published slab band (BUI-1242)** — `graded_fmv` publishes ±15% around the ladder and lone-sale points and floors the exact tier's band at ±15% of its median (BUI-1230 audit). `max_bid` still rides `bid_high`, the pre-widening top, stored in `fmv.bid_high`; the cache hit, `recomputed_cap`, and `over_fmv` (BUI-1262) read it (`min(bid_high, high)`, NULL means `high`). A slab never takes the photo haircut: `graded_fmv` pins `grade_confidence` None, so a direct slab bids 0.80 whatever its collapsed label; the cache hit pins it None too and `recomputed_cap` uses the 0.80 rung on a certified direct row (BUI-1261). A raw direct row reads 0.80 too (BUI-1264): its no-photo bid is 0.80 at any label. When a POST carries the bid's photo grade (`comic_identities[].grade_confidence`, threaded from the working list by `gixen build-batch`/`add-batch` or `gixen add --grade-confidence`, BUI-1266), `recomputed_cap` reads `bid_factor(label, grade_confidence)` at the laxest collapsed label and drops the median cap on a haircut, so a raised photo-haircut bid is advised. A PATCH carries no identity and keeps 0.80. An older server ignores the extra key, but `gixen add --grade-confidence` needs the refreshed console script (`./scripts/deploy.sh`). Deploy the comics server first: `comic-fmv`'s certifier probe also requires the `fmv_bid_high` key, so an older server gets `skipped_schema_mismatch` on every certified row.
