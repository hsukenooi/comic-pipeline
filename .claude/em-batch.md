# em-batch repo profile — comic-pipeline

Loaded by the `/em-batch` skill (`~/.claude/skills/em-batch/SKILL.md`). The doctrine lives there; this file holds only what is specific to this repo. Section names match the skill's §0 contract. When a batch disproves a fact here, update this file at wrap-up.

## Repo shape & conventions

- Python/uv monorepo (`apps/*`, `packages/*`, `plugins/*`, `server/`), ~60k lines. This is the repo the doctrine's evidence was gathered in (the BUI-299..500 batches).
- New tickets → Linear **BUI** team.

## Hot files & import edges

- `server/main.py` / `server/db.py` are the recurring hot pair (all nine tickets in the BUI-383..389 batch touched them).
- The import edge that set the doctrine's rule: BUI-323 refactored `ebay_fetch.py` while BUI-322 imported it — parallel only with public signatures pinned stable.
- The all-hot-file batch happens here (BUI-383..389) but is the **exception**, not the rule — most waves parallelize across packages.

## Context economy

- **Big-file repo: coordinates are line ranges, caller lists, and pasted snippets.** `packages/locg-cli/src/locg/commands.py` is ~5,800 lines — roughly 70k tokens read whole — and a batch routinely puts three agents inside it. Before spawning, grep out the exact line ranges, the real caller list, and the snippet of the pattern to copy: *"Read only `commands.py:3842-4300`; do not read the file whole. The guard to replicate is: `<snippet>`."*
- Name any file safe to read whole (e.g. `metron.py`) and rule out the big files explicitly (BUI-485: the spawn prompt pasted `_disambiguate_series` verbatim and ruled out `commands.py`; the agent never touched the big file).
- Coordinates rot as **stale offsets**: earlier waves rewrite these files, so agents re-grep function/section names and never trust offsets after any merge (2026-07-23: `routes.py`/`commands.py` offsets moved every wave).
- **A grep for a SQL fragment can land in a one-time MIGRATION rather than the live query — confirm the enclosing function before pasting the line number.** These files carry legacy `_migrate_*` helpers whose SELECTs are near-identical to the production ones. 2026-08-12 (BUI-777): the EM grepped `SELECT id, grade, fmv_low, …` in `plugins/gixen-overlay/.../db.py`, got `:602`, and shipped that as the Part 1 target; `:602` is a legacy one-time migration and the real `list_comics` SELECT was at ~2320. The agent caught it, but only because it re-grepped rather than trusting the coordinate — a less careful one would have edited dead code and produced a green PR that changed nothing at runtime. Cheap fix: grep with `-n` and then confirm the nearest preceding `^def `, or grep the *function* first and read within its range.
- **The TICKET's own file path can be wrong — verify every coordinate before pasting it into a spawn prompt.** Same family as the trap above, one level earlier. BUI-788 named `packages/locg-cli/src/locg/locg_lookup.py:64`; the file actually lives in `plugins/gixen-overlay/src/gixen_overlay/`, and only the line number was right. A one-line `grep -rn <SYMBOL>` in EM context costs nothing and saves the agent a wrong-package hunt. Do this for every path a ticket states, especially one filed from an audit rather than written while editing the file.

## Local gates

- `apps/*`: `cd <pkg> && uv run --with pytest pytest`. `packages/*` and `plugins/*`: `uv run pytest`. Report counts per suite.
- **An `apps/ebay` change to `sold_comps.py`'s comp shape or `fetch_book_comps` owes the `apps/fmv` suite too** (`cd apps/fmv && uv run --with pytest pytest -q`): `apps/fmv/tests/test_backfill_comps_ledger.py` replays cached responses through the live `sold_comps` path and diffs every comp field (KTD11). 2026-09-21 (BUI-929): the agent reported apps/ebay green and CI's `apps-python` went red on that replay because slab comps gained three fields. CI's `apps-python` job runs both apps, so the local gate must too.
- **An `apps/fmv` change owes the CI `typecheck` command too** (`uvx mypy --ignore-missing-imports apps/fmv/src/fmv_runner.py plugins/gixen-overlay/src/gixen_overlay/routes.py plugins/gixen-overlay/src/gixen_overlay/ledger.py`): mypy follows imports, so a nullable in `fmv_math.py` goes red through `fmv_runner.py` (PR #524, 2026-09-21). Non-required on `main`, but fix it before merging rather than leaving a red check behind.
- **A pool-shape or exclusion change owes a LIVE re-run on the deployed build before the ticket closes** (BUI-946, 2026-09-21): three measured guards with green replay tests changed nothing in production because the comps ledger re-admitted pre-guard rows. The suite proves the math; only the deployed run proves the plumbing. See `docs/solutions/best-practices/a-fetch-time-exclusion-is-undone-by-an-archive-that-re-admits.md`.
- **A prompt/markdown-only ticket still has a gate: `./scripts/solutions-lint`** (a required CI check). It is the only gate for `.claude/commands/**` and `.claude/agents/**` diffs, which no pytest suite covers — so pair it with a full re-read of the edited files for self-contradiction (BUI-911, 2026-09-09: making crop-writing explicit falsified `comic-grader.md`'s standing "never writes files" claim, which had to be narrowed in the same diff).
- **A `.claude/commands/**` edit ALSO owes `cd plugins/gixen-overlay && uv run pytest -q tests/test_skill_contracts.py`** (part of the required `workspace` job). 2026-09-21 (BUI-919, PR #539): solutions-lint passed and `workspace` went red on `test_no_skill_crossref_is_orphaned`: a cross-skill reference `seller-scan.md § "No silent drops"` named a bold paragraph label, not a heading, and the descriptor is matched WITH its quotes, so even the right heading fails when quoted. Write `file.md § Heading Words` (a real heading, no quotes).

## Review classes

- The doctrine's generic full-fan-out classes apply literally here: **money, concurrency, correctness gates, external/data behavior** — this is where the 6×/$2k over-bid, the seen-set data-loss, and the batch-crash were caught.
- Persona starting map (chosen post-implementation, off the actual diff): a schema/migration change → correctness + adversarial + data-migration; a concurrency change → correctness + adversarial + reliability; a money-math change → correctness + adversarial.

## CI reality

- Five required gates on `main`: `workspace`, `apps-python`, `lint`, `ezship`, `solutions-lint` (BUI-631: branch protection requires all five; `enforce_admins: false`, so an admin can still bypass in a genuine emergency, and `strict: false`, so a branch need not be up-to-date with `main` to merge).
- **`typecheck` is NON-required** — don't block on it or check it per-PR; one glance per batch at wrap-up (`gh pr checks` on the final PR) is enough.
- **CI tests the merge commit against current `main`, not the branch base.** A test that pins the PRE-merge behaviour of a parallel ticket (PR #523 asserted the refusal BUI-939 was fixing, while #522 merged first) goes red only at CI. Parallel agents that pin each other's territory must assert the post-merge outcome, or the EM rebases and rewrites the pin (2026-09-21).
- **`gh pr checks --watch` exits 0 with a required gate FAILED** (re-confirmed 2026-09-21, PR #515: `apps-python fail`, exit 0). The exit code is a timing signal only. Read the per-check lines and `mergeStateStatus == CLEAN` before every merge; branch protection is the backstop, not the watch.
- **`gh pr checks --watch` launched right after `gh pr create` returns at once with `no checks` / all-pending** (2026-09-21, PRs #541/#542): the checks had not registered yet, so the watch is a no-op and the EM re-arms it. `sleep 60` before the watch. Also: `gh pr merge` from a detached-HEAD EM worktree prints `could not determine current branch: ... not on any branch` AFTER merging; benign, the PR is merged and the remote branch deleted, only the local-branch delete is skipped.

## Risk classes

- **A behavior-preserving refactor** → re-run the affected suite locally rather than trusting the agent's reported counts (BUI-389's `server/fallback.py` extraction: the real risk was a `main↔fallback` circular import, so the EM read the import structure and re-ran both suites before merging).
- **A live-repro "X never fires" report can be "X fires and its result is discarded, unreported"** (BUI-921, 2026-09-21): the graded fetch ran on every one of the ticket's three runs; a two-book lot poisoned the ladder, `monotonicity_violations` refused it, and the second pass wrote nothing to `queries_used`/`slab_comps`, so the emitted row was byte-identical to a row that never fetched. Before chasing the gate predicates, check the pass is REPORTED; the fix must include the reporting or the next incident reads the same way. Same batch, 3 of 19 ticket premises were wrong (BUI-933 named a non-existent symbol; BUI-942's "slab path skips the year reader" was one shared gate; BUI-921 above): keep the premise-check + stop license in every spawn prompt, not only opus ones.
- **A schema migration** → apply it against a copy and confirm up/down.
- **A new value for a stored enum column needs a CHECK-constraint migration, and a fresh-schema test suite cannot see that.** 2026-09-22 (BUI-952): `fmv.pricing_basis` carries a `CHECK(... IN (...))` frozen into each existing DB's stored schema; the new `lone_sale` basis passed every test (tests build the schema fresh, with the new value) and would have died on the Mini with an IntegrityError that discards the whole upsert (BUI-593 class). The agent caught it only by checking a production-shaped copy. For any diff that adds a value to a stored vocabulary (`pricing_basis`, `certifier`, `label`, `provenance`, `pool`, `excluded_code`): grep db.py for the column's CHECK and ship the widening migration in the same PR; deploy the server before the client.
- **A count from a proxy measurement is not the rule's count.** 2026-09-22 (BUI-952): the pre-spawn gate counted 22 rungs at effective n in [1, 2) as "lone sales"; the rule requires exactly one fresh sale, and 7 of the 22 held two or three sales. The gate number decides go/no-go, so have the agent re-measure with the rule as implemented and report both numbers; a gate comment posted from the proxy needs a correcting comment.
- **A money-math change** → re-run the pricing path on a known case.
- **A new stitched-row shape in `fmv_runner` needs a `_print_table` test on that exact row.** 2026-09-21 (BUI-928): the end-to-end test ran with the table renderer bypassed (`--brief`), so a `None.__format__` crash on the new row reached main; the live probe found it. Render the row in a test, not only its brief line.
- **A change to an endpoint with a `dry_run`/preview mode** → check that the agent's test exercises BOTH modes, and read the diff for any arithmetic whose correctness depends on which mode is running. BUI-721 added `next_offset = offset + unresolved_count` to `POST /api/comics/backfill-year`; that is right for a real run (a written row leaves the scanned population) and wrong for a dry run (nothing is written, so no row leaves) — a fully-resolving page advanced `next_offset` by zero and looped forever, which is the very stall the ticket existed to fix, on the endpoint's *default* path. The branch's own paging test covered only the all-unresolvable case, where `unresolved_count == scanned` makes the correct and incorrect formulas coincide, so it passed against both implementations. **A test that passes against the buggy implementation too is the thing to look for here** (see `docs/solutions/workflow-issues/verification-whose-failure-is-indistinguishable-from-success.md`), and it is cheap to check: reproduce, then confirm the new regression test fails against the unfixed line before committing.
- **A guard change is verified at the DECISION, on the DEPLOYED build — never at the predicate, never at merge.** BUI-759 widened a hand-priced marker set and proved it against all 999 live `fmv` rows (exactly the right 12 matched, zero false positives). Criterion met, PR green, ready to close — and the guard still protected **1 of 12 rows**, because an eligibility test upstream (`fmv_runner.py`, `_split_by_db_cache`) gated the whole check behind `bool(book.get("locg_id"))` and 11 of 12 books had none. Only a post-deploy probe of the *decision function* caught it (BUI-775). So for any guard/protection/exclusion diff: call the bucketing function over the live population and assert the rows land in the protected bucket, **and neutralize the short-circuits upstream of it** (here `max_age_days=0`, or a fresh cache hit means the guard is never exercised and the run looks protected for the wrong reason). Also compare the guard's identity key against the *writer's* — BUI-775's root cause was the guard keying on `locg_id` while `upsert_comic` keys on `(title, issue, variant)`.
- **`comics-api` defaults `COMICS_CURL_MAX_TIME=30`, which is shorter than several real calls.** `POST /api/comics/backfill-year` blocks ~30s *per row*, so at `limit=5` a call takes ~150s: curl aborts while the server keeps working and commits the page, leaving the caller with no `next_offset` and a blind retry that pages from a stale offset. Export a generous `COMICS_CURL_MAX_TIME` for any long endpoint and build the loop to **halt and reconcile against the store** on a non-zero exit, never to retry. (Same family as `cli.py`'s `_DEFAULT_SERVER_TIMEOUT=15` reporting 36 failures for 11 committed rows.)
- **A guard that reads credentials is verified against the PRODUCTION credential source, not the env.** 2026-09-21 (BUI-929): the printing guard read `EBAY_CLIENT_ID`/`SECRET` from env only, to keep tests isolable; production (`comic-fmv` → `ebay-sold-comps` on the Mini) has no env credentials — they live in `~/.config/ebay-fetch/config.json` — so the guard was inert (every outlier "unverified", none dropped) while every unit test passed. The live spike probe caught it. Check: where does the deployed process get this credential, and does a test prove that source is honored? Isolate in the fixture (repoint the config path), never by having the code avoid the source.
- **A `.backup` copy retains `journal_mode=wal`, so opening it `mode=ro` fails** with "unable to open database file" — a read-only connection cannot create the `-shm` file WAL needs. Open backup copies read-write (they are throwaway) or pass `immutable=1`; the live DB still gets `-readonly`.
- **Probing a write endpoint on the Mini is itself a write, and can look like an outage.** `POST /api/comics/backfill-year` shells out to Metron once per row, so a call takes up to `limit × 30s`; it used to do so ON the event loop, and at `limit=3` the `comics-api` health gate reported "server is not responding" ~90s. That was documented behavior, not a crash — probe write endpoints with `dry_run=true` and `limit=1`, and wait rather than restarting. **BUI-912 (2026-09-21, needs the deploy) moved the shell-out to `asyncio.to_thread`,** so the health gate no longer trips during a pass and a second concurrent pass is refused with **409** instead of silently doubling up; the per-row WALL CLOCK is unchanged, so the caller-timeout rule below still holds in full. **Pass those as a QUERY STRING, not a JSON body** — the handler declares them as scalar FastAPI params (`dry_run: bool = True, active_only: bool = True, limit: int = 25, offset: int = 0`), so a `-d '{"limit": 1}'` body is silently ignored and the call runs at the DEFAULTS instead. 2026-09-09: a probe meant as `limit=1` ran at `limit=25` and blocked the server past a 180s curl timeout, reading as an outage. Correct form: `comics-api POST "/api/comics/backfill-year?dry_run=true&limit=1&active_only=false"`. The defaults here happen to be safe (`dry_run` defaults True), but the silent-ignore is the trap — on an endpoint whose write flag defaulted the other way, the same mistake writes.

## Deploy model

- **Nothing ships on merge.** Deploy actions are manual: service restart via `launchctl kickstart`; install refresh via `uv tool install --force --no-cache` / `uv sync --all-packages`.
- **`apps/ezship` is outside `deploy.sh`.** The skill runs it as `npx tsx src/cli.ts` from the shared checkout, so `git pull --ff-only` there IS the deploy; no restart, no tool install. Probe with `npx tsx -e` importing the changed module (BUI-966, 2026-09-22: asserted exit 3 vs 1 that way). A ticket touching only `apps/ezship` + `.claude/commands/` does not need the full deploy ritual.
- **A bare `git pull` + `launchctl kickstart` HALF-deploys, and `/health` will tell you it fully deployed.** The comics server runs from an editable `.venv`, so restarting it picks up merged `server/` and `plugins/gixen-overlay/` code immediately and `/health` then reports the merged git SHA. The **console scripts are `uv tool install`ed and stay stale** — so a ticket spanning both halves is live on one side only. Observed 2026-09-09: after the BUI-789 ritual's kickstart, `/health` reported the merged SHA while `locg` on PATH was still pre-merge, leaving BUI-788's overlay half live and its `locg-cli` half not. `/health` agreeing with `main` is NOT evidence of a deploy; only `./scripts/deploy.sh` asserts every component.
- Live probe: a `--help` or curl per new endpoint/subcommand on the target — `uv tool install --force` has silently served a stale cached wheel with the new subcommands missing (BUI-455).
- **`./scripts/deploy.sh` runs fine from the EM once the user has said to deploy** (2026-09-21, four runs in one session); the earlier "blocked by the auto-mode classifier" note was a permission-mode artifact. It still refuses a dirty tree, and the shared checkout carries other agents' stray files (`.claude/settings.local.json.bak`, an uncommitted brainstorm doc). **Do not `mv` them: the classifier denies moving anything under `.claude/` (Self-Modification, 2026-09-21).** `git stash push -u -m ... && ./scripts/deploy.sh; git stash pop`, the script's own suggested path, is allowed and restores them. Run from the shared checkout (the server's editable `.venv` and the `--editable` `gixen` install point there) after `git pull --ff-only`.
- **A merged ticket with a live-verification acceptance criterion stays open until the probe runs.** BUI-767 ("verified by looking at a real flagged row, not by reading the CSS") and BUI-759 ("a default `comic-fmv` run leaves all 12 untouched") both merged green and were both still unproven. Comment "shipped in PR #N, deploy action pending" and close only after the probe — closing at merge is how a guard gets marked Done while not running.
- The BUI-383..389 batch shipped two migrations (`bids.group_changed_at` and `group_wins.source` + a unique-index re-key) that sat merged-but-not-deployed until the user asked — the class of thing the deploy checklist exists for.
- **launchd jobs live in `scripts/launchd/*.plist` since BUI-951 (2026-09-22) and `deploy.sh` does NOT install them.** Install by hand from the EM: `cp scripts/launchd/<label>.plist ~/Library/LaunchAgents/ && launchctl load -w ~/Library/LaunchAgents/<label>.plist`, then `launchctl kickstart -k gui/$(id -u)/<label>` for the first run; `~/Library/LaunchAgents` is outside `.claude/`, so the classifier allows it. Read the job's log under `~/.comics-server/<label>.log` and its heartbeat row via `comics-api GET /api/comics/health/heartbeats` (top-level key `jobs`). A scheduled job's "two consecutive runs ping" criterion is proven by kickstarts, not by waiting a month; say so in the closing comment. A job that fetches per book withholds its ping when ONE book fails (BUI-593 rule), so a transient provider error on a single query reads as a failed run: re-kick before diagnosing.

## Data safety

- The doctrine's backup→diff ritual applies as written — it was converged on here (BUI-514), and the BUI-461 backfill over 22 pending rows is the model case of a legitimate, user-gated post-merge production write.
- **The classifier denies ANY Bash that touches `~/.comics-server/db.sqlite`, including the read-only `sqlite3 ... ".backup"` step of the ritual** (2026-09-21, BUI-915, "Modify Shared Resources"). The EM cannot run a file-level production repair even with the user's chat permission; permissions live in settings. Pattern that works: the agent rehearses on a `.backup` copy (agents may read the live file `-readonly`), writes `plan.md` + an asserting, idempotent `repair.py` + a clean diff into the scratchpad, and the ticket is set **Blocked** with the one-line apply command for the user. HTTP mutations via `comics-api POST` ARE allowed: BUI-947's sweep stamped 8 live rows through its endpoint and was verified with `GET ...?include_excluded=true` before/after instead of a file diff. Prefer an endpoint over a file write for any repair that can have one.

## Unattended

- **Viable, in two modes, both local and scheduled on the Mac Mini.** `mode:unattended` (BUI-635) builds and stops at the merge gate. `mode:autonomous` (BUI-972) runs the whole loop and is fired only by `scripts/em-batch-nightly.sh` (LaunchAgent `com.comics.em-batch-nightly`, 01:00; install and knobs in `scripts/launchd/README.md`). The wrapper picks tickets with `scripts/em-batch-nightly-select.py` (team BUI, label `comics`, unassigned, Today/Soon/Someday, cap 8), runs the EM in a fresh detached worktree with `--settings <shared>/.claude/settings.local.json --permission-prompts none`, and posts the EM's final message verbatim to Telegram and the Reflect daily note.
- **Allow rules the run needs, all user-authored in the shared checkout's `.claude/settings.local.json` (27 as of 2026-09-22):** `git *`, `gh pr create|checks|view|list|merge`, `gh run *`, `linear issue view|query|list|comment list`, `scripts/start-work.sh`, `./scripts/deploy.sh`, `./scripts/solutions-lint`, `uv run *`, `uv sync *`, `uv tool install`, `launchctl kickstart`, `comics-api GET|POST`, `comic-fmv`, `ebay-fetch`, `sleep`, and a `Write` rule for the Reflect `daily/` folder; the three `linear issue create|update|comment add` rules live in `~/.claude/settings.json`. `--permission-prompts none` turns a missing rule into a denied step and a held ticket, never a hung job. Never add a rule from inside a run.
- **Hold classes in this repo (autonomous triage):** anything touching `~/.comics-server/db.sqlite` or the collection store at the file level (the classifier denies it anyway; HTTP via `comics-api POST` is fine), any `POLICY_*` env change, any `gixen add|edit|remove` against a real auction, `POST /api/purge`, and provider spend beyond a per-ticket probe (sold-comps.com / SerpApi budgets). BUI-963 and BUI-965 are the standing examples.
- **Deploy safety in autonomous mode:** the shared checkout is where other Herdr agents work and is often left on their branch. Deploy only if it is on `main`, or clean and on a branch already merged into `origin/main` (then `git checkout main` first); stash-park untracked strays; otherwise hold the deploy and say so in the summary.
- **`LINEAR_GUARD_UNATTENDED=1`** is set by the wrapper so the linear-guard Done hook reminds instead of prompting (BUI-878).
- **`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`** is set by the wrapper (24h). Headless `claude -p` otherwise waits at most 10 minutes for in-flight background subagents, then kills them and returns the EM's last message as the summary. The 2026-09-22 12:23 run lost its whole Wave 1 that way ($13, three half-done worktrees, four tickets stranded In Progress). Verified 2026-09-22: with the ceiling raised, the parent waits, resumes on the completion notification, and its final message reflects the agent's report.
