# Comic FMV

Compute fair market value from real eBay sold transactions. No multiplier math — just recent comps in the target condition.

The full math spec — grade parsing, pool-building/widening, IQR trim, grade-curve interpolation, the CGC-proxy fallback, the confidence rubric, caching internals, the stale-install (`comic-fmv --version`) check, the manual fallback (CLI unavailable), and the CLI-debugging Common Mistakes table — lives in `docs/conventions/fmv-math-spec.md`. Read it only when debugging the CLI, building a new consumer, or doing a manual fallback computation. Everything below is what the default path needs.

## How to run

**Default path: `comic-fmv`.** It handles fetch (via `ebay-sold-comps`), cache, dedup, hard-excludes, grade parsing, IQR + quartiles, confidence rubric, self-exclusion, and DB upsert.

Before running, ensure `SOLD_COMPS_KEY` and `SERPAPI_KEY` are set (BUI-545: sold-comps.com is the default primary provider, SerpApi the fallback tier) — source the canonical env file if not:

```bash
set -a && source ~/Projects/comic-pipeline/apps/ebay/.env && set +a
```

Then resolve and health-gate the comics server — **every run, on this default path, not just as a manual fallback** (BUI-439: `comic-fmv` reads `COMICS_SERVER_URL` from env only and hard-fails "must be set" if it's unset — a Mac Mini/MacBook shell that hasn't exported it needs the hostname fallback below, or the CLI dies before it ever queries anything). `comic-fmv` is a **child process**, not an HTTP call this shell makes itself, so it needs the var actually exported into this shell's env (not just resolved inside a one-off `comics-api` subprocess) — `comics_resolve_server` still does that part. Route the health-check itself through `comics-api` (BUI-510) rather than the raw `comics_health_gate` call, so it shares the exact same call path every other skill's server check uses:

```bash
source "$(git rev-parse --show-toplevel)/scripts/comics-server.sh"
comics_resolve_server || exit 1   # exports COMICS_SERVER_URL for comic-fmv below
comics-api GET /health >/dev/null || exit 1   # the server must answer
```

If either step fails, **stop immediately** — the comics server is unreachable or the machine is unrecognised, so FMV data cannot be saved. Do not proceed with any queries.

```bash
comic-fmv --batch <working_list.json> --out <results.json> --brief
```

`--batch` JSON shape: `[{item_id, title, issue, year, publisher?, variant?, grade, grade_confidence?, locg_id?, locg_variant_id?, notes?}, ...]`

Literal example (build it directly — the shape is documented here, don't grep `apps/fmv` source for it): `[{"item_id": "115834720199", "title": "Fantastic Four", "issue": "16", "year": 1963, "publisher": "Marvel", "grade": "VG 4.0", "grade_confidence": "medium"}]`

`publisher` and `variant` are optional but **load-bearing** (BUI-161). `variant` (e.g. `Newsstand`, `Direct`) gives base vs variant editions distinct `comic_id`s (BUI-28), so omitting it conflates two sub-markets onto one comic.

**A row carrying `certifier` is a certified slab, not a raw comic (BUI-930)** — see § Graded (slab) pricing mode below for its own batch keys and pricing rules.

**Pass `publisher` whenever you know it — including Marvel and DC (BUI-566).** `ebay-sold-comps` decides per-publisher what to do with the field in **one** place (`_publisher_qualifier`), so there is no publisher you should deliberately withhold.

- **Marvel** → appends the canonical `marvel comics` (BUI-315). This is what keeps a **year-less** query like `"X-Men 97"` from pulling in non-comic merchandise (the 2024 *X-Men '97* show). Omitting `publisher` disables it with no warning.
- **DC**, and DC/Marvel imprints (Vertigo, Wildstorm, Epic, …) → appends **nothing**. A two-token `dc comics` qualifier measurably narrowed recall (it roughly halved the pool on Batman #232 and Detective #400, measured on SerpApi — BUI-315/BUI-321), so DC short-circuits to no qualifier at all. Passing `DC` is a safe no-op — the query is byte-for-byte the same as omitting it.
- **Indie** (Image, Dark Horse, Valiant, …) → appends the name verbatim. This is the primary noise filter that keeps trading cards, toys, and unrelated goods out of the pool (BUI-161).

**Don't guess it, though.** An absent `publisher` is safe (the base query passes through untouched); a *wrong* one is not — a misattributed indie or Marvel name appends a term that narrows the pool to nothing or to the wrong market. Pass it when you actually know the publisher; leave it out when you don't.

**What the Marvel qualifier does *not* do:** it cannot separate two *Marvel* volumes that share an issue number — X-Men Vol. 1 #85 and Vol. 2 #85 are both `marvel comics`. Only `year` disambiguates a same-publisher relaunch, so a **year-less** pre-2000 book on a relaunched masthead can still price off a pool polluted with cheap modern issues (the signature: a suspiciously low range and a LOW/degenerate confidence, while a sibling issue above the relaunch's issue ceiling prices cleanly and HIGH). Treat that as a signal to supply `year`, not as a reason to re-run. The qualifier's effect on sold-comps.com (the current primary) is unmeasured.

`grade_confidence` (optional, `high`|`medium`|`medium-low`|`low` — **four** levels, BUI-162) is the photo-coverage confidence from `/comic:grade`. When present and low, it haircuts the max bid — `medium-low` and `low` haircut **differently** (0.70 vs 0.60), so don't collapse them. Absent → standard 80% bid, no haircut (back-compat for seller-stated grades and manual runs).

**`title` is normalized automatically (BUI-346)** — you don't need to hand-clean it before building the working list. `comic-fmv` strips a leading article (`The`/`A`/`An`) and an embedded `#<issue>` (or bare trailing issue number) that duplicates the separate `issue` field, before the title ever reaches `ebay-sold-comps` (otherwise `"The Amazing Spider-Man #50"` plus `issue: "50"` builds the doubled query `"The Amazing Spider-Man #50 50"` and returns nothing). `ebay-sold-comps`' `build_query` carries the same normalization as a second, independent layer, so a title that reaches it un-normalized (e.g. a direct `--title` CLI call) is still safe.

Flags:
- `--max-age-days N` (default 7): reuse FMVs already in the comics server's DB if `fmv_updated_at` is within N days
- `--force`: bypass both the SerpApi cache and the DB cache and recompute everything. **It cannot clear a `one_sided`/`too_wide` flag** — it refetches the *same* market and re-flags identically. To move a flagged book, change the input (`title`/`publisher`/`year`) or widen `--grade-window`; a bare `--force` retry is a wasted no-op. **Hand-priced rows (BUI-769):** a row is hand-priced when its **`fmv.provenance` column is `'hand'`** — or, for a row written before that column existed, when its `fmv_notes` *opens with* the word `hand` or `manual` in any capitalization (`hand §`, `hand OVERRIDE`, `manual:`, `Manual:` — an operator's manual override, e.g. Batman #251). Such a row is skipped entirely by a default run — reported as `skipped N hand-priced row(s) (use --force to overwrite)` and a `skipped_hand_priced` source on that row — even when it's stale enough that normal cache logic would otherwise recompute it. Only `--force` overwrites one, and it echoes the old hand notes to stderr first so they aren't silently lost.

**When you hand-price a row, POST `fmv_provenance: "hand"` (BUI-769).** The column is the claim: it cannot be lost to a reworded note, and a mistyped value **422s loudly** — `fmv_provenance` accepts only `hand` or `machine`. (Legacy rows are still recognised by the `hand`/`manual` notes prefix, which fails open to any reword — don't rely on it for new rows.) Keep writing a descriptive note as well; it is the reasoning, which is the part that cannot be recomputed. Every `comic-fmv`-computed row posts `fmv_provenance: "machine"` automatically.
- `--grade-window N` (default 2.0): raise or lower the comp-pool widening ceiling — does **not** bypass the one-sided/too-wide guards (a guarded book still flags `needs_manual`)
- `--brief`: after the table, print one compact JSON object per row on stdout (`item_id`, `comic_id`, `fmv_id`, `max_bid`, `flag_reason`, `confidence`, `fmv_low`, `fmv_high`, `fmv_notes` — BUI-505; `source` — BUI-549; `certifier`, `label`, `pricing_basis` — BUI-930; `provenance` — BUI-949; `active_ask_low`, `active_ask_n` — BUI-954, both `null` except on a refused row that found a matching active listing) — the linkage + pricing fields to carry forward, without re-reading the full `--out` file. `source: "skipped_lookup_error"` marks a row the comics-server lookup FAILED for — left completely untouched, not a genuine zero-comps book — distinguishable from an ordinary unpriced row, which has the same null pricing fields but a different `source`. `source: "ledger-advisory"` (BUI-663) is the opposite shape and the one to watch: it has a real `fmv_low`/`fmv_high` and a `null` `flag_reason`, so it looks priced — but `max_bid` is `null` and nothing was persisted. See the `ledger-advisory` note below the `--out` schema. `source: "skipped_schema_mismatch"` (BUI-930) is the certified-row counterpart of `skipped_lookup_error` — see § Graded (slab) pricing mode below. `certifier`/`label`/`pricing_basis` are `null` on a raw row and carry the price identity plus how the band was produced (`direct`|`lone_sale`|`interpolated`|`ladder`|`proxy`) on a priced one. `provenance` (BUI-949) is a short "what the price rests on" string, never `null` (never re-derive it by parsing `fmv_notes` — read it straight off this key): a certified row names the tier and its count (`exact n2`, `ladder 4 rungs`), plus `pq widened`/`ledger-drop N` when they apply, or `refused <reason>` when the row punted; a raw row names the tier and comp count (`direct n7`, `interpolated n5`, `proxy n3`) plus `haircut grade`/`haircut fmv`/`haircut both` when the bid factor is below 0.80; an unpriced/no-comps/skipped row reads `n/a` or its flag/skip token (`one_sided`, `skip:unverified`, `fetch-err`, …). Use it for the two decisions that matter — stopping on a Buy It Now listing, and approving/overriding an auction's bid — not as a substitute for `fmv_notes`, which stays the full audit trail.
- `--quiet`: suppress the human table on stdout (combine with `--brief` for JSON lines only)
- `--server-url URL`: override `COMICS_SERVER_URL`/`GIXEN_SERVER_URL` for this run
- `--version`: print the installed version plus the git SHA/date the binary was built from, then exit

The CLI prints a human-readable table to stdout and writes the full structured result to `--out` on disk. Present the table to the user. **Carry the `--brief` JSON lines forward to Step 4 of `/comic:buy`** (`item_id`, `comic_id`, `fmv_id`, `max_bid`, `flag_reason`, `confidence`, plus `fmv_low`/`fmv_high`/`fmv_notes` for the range + haircut presentation (BUI-505), `source` to tell a lookup-error skip apart from an ordinary unpriced row (BUI-549), and `provenance` for the short basis cell to show at the Buy It Now stop and the auction approval gate (BUI-949)) — don't re-read the full `--out` JSON for linkage; the `--out` file on disk stays available if you need a full row (`queries_used`, `trimmed_pool`, etc.) for debugging.

**`--out` row schema** (one object per book; use these exact keys — do **not** guess `comp_pool`/`pool`/`prices`):
- Top-level: `input`, `fmv`, `comp_count_total`, `queries_used`, `db_row`, `comic_id`, `fmv_id`, `source` (`fresh`|`cached`|`cgc-proxy`|`ledger-advisory`|`error`), `breaker_tripped` (BUI-535, on rows that ran a live fetch — see § Provider request budget). `comic_id`/`fmv_id` are top-level on fresh/proxy rows; on `cached` rows read them off `db_row` (`id`/`fmv_id`). A `ledger-advisory` row (BUI-663) has `comic_id`/`fmv_id`/`db_row` all `null` — nothing was written — and additionally carries `ledger_comic_id` (which book the ledger read resolved to) and `ledger_rows` (how many stored comps answered).
- The surviving comps are **nested** at `fmv.trimmed_pool`, alongside `fmv.median`/`fmv_low`/`fmv_high`/`max_bid`/`bid_factor`/`flag_reason`/`confidence`/`window`. `fmv.non_usd_dropped` (BUI-678, absent on an old cached row — treat as 0) is the currency-gate count described below.

When you do need a pool field, **project it in one shot — never Read the whole `--out` file** (it's dominated by `queries_used`/`trimmed_pool`):

```bash
python3 -c "import json; print([(x['input']['item_id'], (x.get('fmv') or {}).get('trimmed_pool'), x['queries_used']) for x in json.load(open('<results.json>'))])"
```

**`fetch-err` ≠ `n/a` (BUI-143):** a row whose FMV column reads `fetch-err` (and the loud post-table warning) means the **sold-comps fetch failed** for that book — since BUI-545 that means **both providers** (sold-comps.com primary AND the SerpApi fallback) errored — **not** that the book has no comps. Treat a `fetch-err` row (or a whole batch that comes back all `fetch-err`/`n/a`) as a provider failure: check `SOLD_COMPS_KEY`/quota first (free tier is 100 req/mo), then SerpApi, and re-run. Never tell the user these books are illiquid or bid on them as if priced.

**A third category: `0 comps (N non-USD dropped)` ≠ a genuine no-comps book (BUI-678).** `ebay-sold-comps` gates every comp on `price.raw` proving USD (BUI-675) — a real defense against pricing a book off a foreign-currency listing taken at face value. That flip happens per **response**, not per listing, so occasionally a book's fetch succeeds (`queries_used` is clean, no `error` key anywhere — this is NOT a `fetch-err`) and the parse still rejects every result it got back. A row in this state renders as `0 comps (N non-USD dropped)` instead of the bare `n/a` a genuine no-comps book gets, carries a `non_usd_dropped=N` token in `fmv_notes`, and the run prints an unconditional stderr warning naming how many books/comps were affected. **Do not** read this as "illiquid" (like a bare `n/a`) or as a provider outage (like `fetch-err`) — it means real sold comps existed and were deliberately discarded for a currency this pipeline won't trust. This is diagnostic only — deliberately **not** a `flag_reason` (it isn't a pricing verdict, and the row has no more of a bid-able number than any other empty pool) — so it still renders with `source: "fresh"` and a null `flag_reason`, same as a genuine no-comps book; the count is what tells the two apart. There is no reintroduction path (the gate is correct and stays as-is): hand-price the book, same as any other unpriced (n=0) row.

**`ledger-advisory` ≠ a price (BUI-663):** when the fetch fails, `comic-fmv` now tries to price the book from the **comps ledger** — the archive of comps every past run stored (BUI-656/658). Such a row renders as `$low–$high LEDGER` with `advisory` in the **Max bid** column, carries `source: "ledger-advisory"`, and its `fmv_notes` lead with `LEDGER-ADVISORY (stale comps, no bid cap)`. Read it as a **starting point for a hand-priced cap, never as one**:

- **It has no `max_bid`, deliberately.** The band is computed by the same `compute_fmv` math as a live row, and the cap is then withheld — the same way a `needs_manual` row withholds it. Do not derive one by multiplying `fmv_high` yourself.
- **Its `flag_reason` is `null`**, so a check that gates only on `flag_reason` will miss it. **Gate on `source`.**
- **Nothing was written.** `comic_id`, `fmv_id` and `db_row` are all `null`: there is no `fmv` row for a snipe to link to, `/comic:verify` will report `no_comic` for it, and it will never appear on the `/comics` dashboard. That is by design — it is also why a later run can never re-serve this number as an innocuous `source: "cached"`.
- **The fetch still failed.** The row stays inside the `fetch-err` count and the loud warning above; the advisory is an addition to that report, not a replacement for it. Fix the provider and re-run to get a real price.
- **It is not the number a live run would produce.** It prices from stored comps only, with no first-party outcomes merged in (BUI-286), and it is emitted only when the trimmed ledger pool holds **≥3** comps — BUI-663 measured that the hazard of a ledger price is pool *thinness*, not comp *age* (both providers serve only a ~90-day sold window, so there is nothing for a staleness cutoff to cut). A thinner ledger pool, or one the pool-shape guards flag, produces no band at all — just the plain `fetch-err`.

## Graded (slab) pricing mode (BUI-930)

A row carrying `certifier` (`cgc`|`cbcs`|`other`) is a **certified slab**, not a raw comic — send it with four extra batch keys instead of relying on a raw `grade`/`grade_confidence` pair: `certifier`, `label` (`universal`|`signature_series`|`qualified`|`restored`|`conserved`, default `universal`), `page_quality` (`white`|`ow_w`|`ow`|`c_ow`|`cream`|`unknown`), and `cert_number`. `listing_type: "BIN"` still matters on a certified row — unlike a raw BIN listing (skipped upstream at Step 1), a BIN slab is still fetched, priced, and written; only `max_bid` is withheld (R34). **`grade_confidence` is ignored for a certified row** — a sealed CGC/CBCS grade carries no photo-assessment risk to haircut.

The full math — the deploy-order probe, the exact/ladder decision, ledger weighting, page-quality preference, the printing guard — lives in `docs/conventions/fmv-math-spec.md` §7b. What the default path needs:

- **Only Universal (blue label) CGC/CBCS slabs are auto-priced.** Signature Series, Qualified, Restored, Conserved, and any certifier other than CGC/CBCS punt to `needs_manual` before any fetch: `label_signature_series`, `label_qualified`, `label_restored`, `label_conserved`, `certifier_other`. `no_certifier_pool` (no slab comps survive the identity/age filters) also punts before pricing.
- **A certified row never touches the raw market.** No raw pool, no CGC-proxy rescue, no cross check, no ungraded anchor, no first-party comps — and §7a's raw discount factors never apply to it.
- **Exact tier vs. lone-sale tier vs. ladder tier.** At effective n ≥ 2 sales exactly at the target grade, it prices directly (`pricing_basis: "direct"`, the standard confidence rubric on effective n/CV, envelope-clamped below effective n 3). Below that, if the exact grade holds **exactly one fresh sale** (weight 1.0, i.e. sold within 90 days) and the nearest anchor-eligible rungs below and above both bracket that sale while sitting within 3x of each other, the row is priced **at the sale** — `fmv_low == fmv_high == median`, `pricing_basis: "lone_sale"`, confidence LOW, bid factor **0.70** (BUI-952). Its Provenance cell reads `lone sale $900`. Everything the lone-sale tier declines — two sales, a stale sale, a sale outside its bracket, a bracket wider than 3x, a missing side — falls through to the ladder exactly as before, so it never turns a priced row into a refusal. Otherwise the target rung is dropped from the ladder and neighbouring rungs interpolate — which on vintage slabs routinely hold only one sale each, and that's still allowed to anchor — at `pricing_basis: "ladder"`, confidence LOW, bid factor 0.60. Ladder refusals: `ladder_too_thin` (<3 usable rungs after dropping the target), `ladder_non_monotone` (the target's two bracketing rungs invert), `outside_ladder` (the target sits past the observed rungs — never extrapolated).
- **A ladder refusal still carries its evidence (BUI-940).** `ladder_too_thin`/`ladder_non_monotone`/`outside_ladder` all keep whatever the pricing math had already looked at: the exact-grade sale(s) with sold date, and the nearest anchor-eligible rung below and above the target (one side may be `null`, e.g. `outside_ladder`). It rides `fmv_notes` as `exact=$700@2026-09-17`, `below=4:$1400 n1`, `above=5.5:$899 n1`, and the human table's FMV cell prints it after the `manual:<reason>` token — no need to reopen the results file to hand-price the row. A pre-fetch punt (`label_*`/`certifier_other`) never fetched comps, so it carries none of this.
- **Schema-mismatch skip.** Before pricing any certified row, `comic-fmv` probes the comics server for a `certifier` key on `GET /api/comics`; a server that predates BUI-924/925 lacks it, and every certified row in the batch gets `source: "skipped_schema_mismatch"` with zero fetch and zero write — same shape as `skipped_lookup_error` above (a system failure, not a pricing verdict), because on an old server a slab price would silently overwrite the raw row at the same grade.
- **`pricing_basis` rides the brief line.** `--brief` emits `certifier`, `label`, `pricing_basis` alongside the existing keys (`null` on a raw row, unchanged for every prior consumer), so a cache hit reproduces the same confidence and bid factor a fresh ladder row got.
- **`provenance` (BUI-949) is the short cell version of all this** — `exact n<count>`/`ladder <N> rungs`, plus `pq widened`/`ledger-drop <N>` when they apply, or `refused <reason>` on a punt — in both the table and `--brief`. See the Provenance column bullet under § Reading the output table for the full token list.

## Provider request budget (BUI-570)

The sold-comps providers are a **shared, finite budget**, and a batch spends far more than one request per book. Read this before running anything above ~50 books.

**A book is not one request.** `ebay-sold-comps` runs a tiered strategy per book: a base query always, plus a gated page-2 fetch, a broadened (year-dropped) tier, a grade-targeted tier, and a vintage "inclusive" tier — each conditional, up to five live queries for a thin vintage book. Each of those can additionally cost **two** provider requests, since a failing sold-comps.com query fails over to SerpApi (BUI-545). A 66-book batch is a low-hundreds-of-requests batch, not a 66-request one.

**The 7-day query cache is what makes a re-run cheap — but only for an *identical* query.** Re-running the same books inside 7 days is served from cache and costs nothing. Two things void that: `--force` bypasses the cache and re-spends the whole batch, every tier; and **changing any query input re-prices from scratch** — adding a `publisher`, filling in a `year`, or correcting a `title` builds a different query string, so it misses the cache by design. Budget a corrected batch as a full-price run, not a cheap retry. (Per the `--force` note above it also cannot clear a `one_sided`/`too_wide` flag, so a bare `--force` retry is a wasted no-op that drains the budget for nothing.)

**Re-runs compound; the breaker resets.** The BUI-535 circuit breaker is scoped to **one** `ebay-sold-comps` invocation, so every fresh `comic-fmv` call starts with a clean, untripped breaker — but the providers' rate limit and monthly quota do **not** reset. This is the part that misleads operators: a new run re-arms the safety, not the budget. Four runs in a row can each pay the breaker's 5-consecutive-error trip cost on the way down while the quota drains straight through.

**So don't chop a batch up, and don't probe-then-re-run.** Because the breaker is per-invocation, splitting 60 books into three runs of 20 re-arms the trip cost three times instead of paying it once. Run the full set in **one** `comic-fmv --batch` call and read the result. When investigating a suspected pricing problem, design that single pass to answer the question — a small probe followed by a large re-run is exactly what exhausts the budget.

**One batch is safe at any size (BUI-701).** `sold_comps.py` paces its own sold-comps.com dispatch in code (~48 req/min, ~20% under the provider's 60 req/min ceiling, shared across all worker threads) and gives a 429 a long, jittered backoff, so a single invocation fits the rate window on its own (a 200-book batch is covered by a mocked-clock test). **Don't chunk a batch by hand to dodge 429s** — it doesn't help, and it pays the breaker-reset cost this section warns against.

**There is no `--max-workers` on `comic-fmv`.** That flag exists on `ebay-sold-comps`, which `comic-fmv` invokes with a fixed command line, so it cannot be set from this path — do not offer it to the user. Batch composition and `--force` discipline are the only levers here; concurrency is not one of them (sold-comps.com is separately capped at 4 concurrent requests internally and, since BUI-701, paced below its rate ceiling in code — so the knob would be near-inert for the default primary anyway).

**A budget-exhausted zero looks exactly like an illiquid book.** A breaker-tripped fetch returns `comps=0` — shape-identical to a genuine no-comps book. After any large or repeated run, check `breaker_tripped` before telling the user a book is illiquid, and watch stderr for `<provider> appears down — N consecutive errors, circuit breaker tripped (BUI-535)`. Same discipline as the `fetch-err` ≠ `n/a` rule above.

```bash
python3 -c "import json; r=json.load(open('<results.json>')); print(sum(1 for x in r if x.get('breaker_tripped')), 'of', len(r), 'rows affected by a tripped breaker')"
```

## Reading the output table

```
| # | Comic | Grade | FMV Range | Median | n | Window | CV | Confidence | Provenance | Notes |
|---|---|---|---|---|---|---|---|---|---|---|
| 1 | X-Men #31 (1967) | VF+ 8.5 | $100-175 | $135 | 9 | ±0.5 | 22% | HIGH | direct n9 | — |
| 4 | FF #63 (1967) | NM+ 9.6 | needs_manual | — | 5 | ±1.0 | n/a | — | one_sided | manual_review=one_sided |
| 5 | Batman #227 (1970) | CGC 4.5 | manual:ladder_non_monotone exact=$700@2026-09-17 below=4:$1400 n1 above=5.5:$899 n1 | — | 0 | n/a | n/a | — | refused ladder_non_monotone | manual_review=ladder_non_monotone |
```

- **`needs_manual` reasons (raw)** — `too_sparse` (fewer than 2 comps survive IQR trim), `one_sided` (every comp sits on one side of the target grade, no bracket), `too_wide` (the pool brackets the target but spans more than 2.0 grade points), `variant_dropped` (BUI-588 — no comps existed until the book's `variant` term was dropped, so the pool prices the **base cover**, not that variant; the dropped text is named in the notes as `variant_dropped=<text>`, and unlike the other three this one clears by fixing/removing the input `variant`, not by `--force`). A flagged book still gets a linked, traceable comic stub (`comic_id`, `manual_review=<reason>` in notes) but emits **no bid-able number** — never invent one from the smeared/one-sided pool; hand-price via the math spec's §7/§7a or leave it for manual review. **`needs_manual` reasons (certified, BUI-930)** — see § Graded (slab) pricing mode above: `label_signature_series`/`label_qualified`/`label_restored`/`label_conserved`/`certifier_other`/`no_certifier_pool`/`ladder_too_thin`/`ladder_non_monotone`/`outside_ladder`.
- **A refused graded row's FMV cell carries its evidence (BUI-940)** — row 5 above: the exact-grade sale(s) (`exact=$price@sold_date`) and the nearest rung below/above the target (`below=grade:$median nN`, `above=grade:$median nN`), same tokens as in `fmv_notes`. Either may be missing — a one-sided `outside_ladder` refusal has no `above` (or no `below`), and a pre-fetch punt (`label_*`/`certifier_other`) has neither, since it never fetched comps.
- **The Provenance column (BUI-949) is the short "what the price rests on" cell — read this before the numbers, not after.** It's built from the structured `fmv` fields and `pricing_basis`, never from parsing `fmv_notes`, so it can't drift from a reworded note. A priced **raw** row names the tier it priced on plus the comp count — `direct n9`, `interpolated n5`, `proxy n3` — and, only when the bid factor is below the standard 0.80, which confidence input set it: `haircut grade` (the `/comic:grade` photo confidence was the binding constraint), `haircut fmv` (the comp-pool confidence was — this is also what you'll see on every `interpolated`/`proxy` row with no `grade_confidence` attached, since the tier's own cap is what's biting), or `haircut both` (tied). A priced **certified** row names the tier and its count — `exact n2` (effective n ≥ 2 at the target grade), `lone sale $900` (BUI-952: one fresh sale at the target grade, bracketed by its neighbouring rungs, priced at that sale), `ladder 4 rungs` (the target rung was dropped and interpolated across N anchor-eligible neighbours) — plus `pq widened` when the same-page-quality pool was too thin and widened to all qualities, and `ledger-drop N` when N ledger comps were excluded as pre-guard duplicates. A **refused** row (raw or certified) reads its flag reason bare (`one_sided`) or prefixed `refused` for a certified punt (`refused ladder_too_thin`) — same vocabulary as the FMV cell's `manual:<reason>`/`manual:<reason> <evidence>`, just without the evidence tokens. It may carry an appended `— asks from $X (nN)` (BUI-954): read this as a **ceiling**, not a price — it's the lowest active Buy It Now ask matching the row's identity (same title/issue/grade, and on a certified row the same certifier/label), and the spike review that motivated it found unsold asks routinely sitting above sold prices. Never treat it as a bid-able number; `fmv_low`/`fmv_high`/`max_bid` are unaffected by it either way. An **unpriced/no-comps/skipped** row reads `n/a`, or the same distinct skip token the FMV/Source columns already use (`skip:unverified`, `skip:schema`, `skip:422`, `fetch-err`) rather than a bland `n/a` that would misread as "illiquid" (BUI-143). On a cache hit, a certified `ladder` row's rung count is not reconstructable (BUI-930 never persists the per-rung breakdown) and renders as the bare `ladder` token — this is a known, accepted gap, not a bug.
- **`first_party=<count>` token** in `fmv_notes` — `fmv_comps`/`N` isn't purely a SerpApi count; it may fold in first-party comps from your own resolved WON/LOST auctions for that `(comic, grade)`. Check for this token before assuming `N` is all SerpApi.
- **CGC-proxy rows** — notes carry `CGC proxy: … n=<count> is graded-ladder comps, not raw-market depth`. Never read a proxy row's `N` as raw-market liquidity.

When presenting the table to the user, always surface: the window the pool was built at, N and CV, whether the book flagged `needs_manual` (and why) vs. auto-priced, whether grade-curve interpolation was applied, suspect comps (with reason), and a hot-market signal if the current bid already exceeds the computed Q75.

**Hot-market signal → flag only; never re-derive (BUI-530).** The signal fires when a live auction's current bid (from `/comic:identify`) already exceeds the computed Q75 (= `fmv.fmv_high`). The response is a **fixed rule, not a judgment call**: surface it to the user as a flag and leave `max_bid` exactly as `comic-fmv` computed it — **apply zero bid-factor adjustment**. Do **not** re-fetch comps and do **not** hand-rebuild or re-derive the comp pool to "justify" a bump — the pool `comic-fmv` already priced is the pool, and re-deriving it by hand cannot change the verdict. Bidding above the computed cap on a hot auction is the user's explicit call, never an automatic skill adjustment.

**When to dig into a pool.** Open `fmv.trimmed_pool` / `queries_used` only when (a) `flag_reason` is set (`one_sided`/`too_wide`/`too_sparse`), or (b) the table numerically contradicts the live bid (the hot-market signal above — and even then, dig only to *report*, per the rule above, never to re-price). A `LOW` confidence **alone is not a reason to dig** — LOW is already `comic-fmv`'s verdict on that pool; reproducing the pool by hand won't change it.

**Cross-grade inversion sweep → advisory report, not part of a pricing run (BUI-583).** `comic-fmv --inversion-sweep` reports books where two grades of the *same* `comic_id` are priced backwards — a higher grade below a lower one (X-Men #83: 4.0 = $35–70 but 7.0 = $5–45). It reads existing DB rows only, so it costs **zero provider requests** and is safe to run any time — it is exempt from the per-invocation request-budget rule above. It is **not** a `flag_reason`: no row is flagged, nothing is written, and no price changes, so this never gates `/comic:buy` Step 3. Inversions are invisible to every other mark, which judges one pool in isolation. When one fires, one of the pair's two pools is wrong — decide by hand which, then `comic-fmv --force` that book or hand-price the bad row. Do not bulk-re-run the whole set on the strength of the report.

**`anchor_diverges` token → flag only; never re-derive (BUI-534).** `fmv_notes` may carry an `ungraded_anchor=$X (n=N raw)` token (the median of the grade-less comps the pool dropped, BUI-522) followed by `anchor_diverges=1` when the priced range sits far outside that anchor (e.g. Batman #251, 2026-07-24: pool $400–425 vs anchor $224.8 off 36 raw sales — the graded pool was pricing a different market than the bulk of raw trades). Same fixed rule as the hot-market signal above: surface it to the user as a flag and leave `fmv_low`/`fmv_high`/`max_bid` exactly as `comic-fmv` computed them. Do **not** re-fetch comps, re-derive the pool, or treat the anchor as a truer price — it's a coarse sanity/liquidity signal, not a repricing input. If the divergence looks wrong on inspection, that's a candidate for a hand-priced override (see the math spec), not a `comic-fmv` re-run.

**`proxy_below_anchor` token → flag only, CGC-proxy rows (BUI-980).** A CGC-proxy band (proxy `n=<count>` in Provenance) may carry a `proxy_below_anchor=1` token alongside `ungraded_anchor=$X (n=N raw)` when the proxy's own top (`fmv_high`) sits below that same book's raw-comps anchor and the anchor has at least 8 raw sales (e.g. Batman #227: band top $500 vs anchor $609 off 18 raw sales). BUI-976 found the proxy factor runs systematically low against real raw/slab pairs, but too unevenly to retune as a single constant — this flags the worst misses instead of repricing them. Same fixed rule as `anchor_diverges` above: never re-derive the pool or bump the band — it's a signal for a hand-priced override, not a repricing input.

**`ask_ceiling` token → display only, on refused rows (BUI-954).** A row that ends the run refused (raw or certified) fetches active Buy It Now asks for the same identity and, when it finds any, carries an `ask_ceiling=$X (nN)` token in `fmv_notes` and an `active_ask_low`/`active_ask_n` pair in `--brief` and the `--out` JSON. Same contract as the ungraded anchor above: informational only, never a repricing input — the ask enters no pool, moves no guard, sets no cap, and is never stored as a comp. Read it the way the name says: a **ceiling**, the most a seller currently wants for this identity, not evidence of what it's worth. Absent (both `null`/no token) whenever the search found nothing matching, the `ebay-fetch` subprocess failed, or the row priced normally — a priced row never triggers this search at all. See `docs/conventions/fmv-math-spec.md` §7c for the full identity-filtering rule.

## Save to DB

`comic-fmv` upserts each priced comic into the comics server's `comics` table automatically (`POST /api/comics`) right after computing FMV — this is the authoritative comic-metadata write `/comic:snipe-add` later links a bid to; no manual step is needed on the default path. See `docs/conventions/fmv-math-spec.md` for the manual `curl` equivalent and full field semantics (needed only if `comic-fmv` is unavailable).
